# Product Goals

## One-line goal

**Execute declarative DAG workflows durably and predictably across persistent services, asynchronous jobs, workers, and heterogeneous compute runtimes, while keeping domain semantics and physical resource scheduling outside the engine.**

## G1 — Durable workflow execution

A submitted workflow must not disappear because an Andormu process restarts. The engine must recover its orchestration state and continue from durable records.

## G2 — Precise execution semantics

For every node and edge, users must be able to answer:

- Why is this task blocked, ready, running, skipped, failed, or complete?
- What dependency rule caused the transition?
- Which attempt is active?
- Which retry policy applies?
- What will happen after failure, cancellation, or timeout?

## G3 — Generic shared engine

The same engine must execute workflows generated by Zidormi, Anachronos, Evaluation, Simulation, Synthetic Data, and future platforms without importing their domain code.

## G4 — Reliable recovery

Different failure scopes must have different recovery semantics:

- Engine/process crash → automatic reconciliation.
- Task attempt failure → retry policy.
- Lost execution backend → attempt recovery/failure classification.
- Terminal workflow failure → explicit redrive/restart.

## G5 — Versioned reproducibility

A run pins an immutable execution snapshot. A redrive must not silently change the workflow definition, task definition, or execution policy.

## G6 — Strong operational visibility

Operators need a graph, state timeline, task-attempt history, errors, events, log links, resource references, and recovery actions without reading raw backend objects.

## G7 — Runtime portability

Andormu core semantics must not require Kubernetes, Slurm, Ray, or any single runtime. Backend-specific behavior belongs behind adapters/contracts.

## G8 — Safe dynamic workflows

Conditional branches, fan-out, and subworkflows should be possible without sacrificing durable recovery. Dynamic expansion must be explicit and durably recorded before expanded nodes run.

## G9 — Interoperable events

External lifecycle events should be representable in a CloudEvents-compatible envelope. Lineage integrations such as OpenLineage should be adapters, not Andormu's core state model.

## G10 — Product-quality governance

Multi-tenant namespaces, RBAC, audit, API idempotency, versioning, and compatibility must be designed before implementation.


## G11 — Service-first execution compatibility

A logical task must be executable by an already-running service or worker without requiring process/container lifecycle to equal task lifecycle.

## G12 — Backpressure and high-volume dispatch safety

Andormu must be able to keep dependency-ready work queued/admitted safely instead of flooding a constrained service or worker pool. Logical dispatch admission must remain distinct from physical resource admission.

## G13 — Domain-owned workflow selection

Domain platforms choose or compile the correct workflow for their data/business semantics. Andormu instantiates and executes the supplied workflow without embedding file-type, training, or other domain routing rules.
