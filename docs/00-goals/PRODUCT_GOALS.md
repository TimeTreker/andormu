# Product Goals

## One-line goal

**Provide the vendor-neutral durable control plane for Timeways: execute Bronze Dragonflight declarative DAG workflows predictably across cloud and on-prem services, workers, data engines, and compute runtimes while owning logical orchestration semantics and admission but reusing standard infrastructure and external physical scheduling.**

## G1 — Durable workflow execution

A submitted workflow must not disappear because an Andormu process restarts. The engine must recover its orchestration state and continue from durable records.

## G2 — Precise execution semantics

For every node and edge, users must be able to answer:

- Why is this task blocked, ready, running, skipped, failed, or complete?
- What dependency rule caused the transition?
- Which attempt is active?
- Which retry policy applies?
- What will happen after failure, cancellation, or timeout?

## G3 — Timeways durable control plane

Andormu is the durable control plane of Timeways, the Bronze Dragonflight vendor-neutral execution platform. Timeways integrates standard execution/data infrastructure rather than replacing it.

## G4 — Generic shared engine

The same Andormu semantics must execute workflows generated by Zidormi, Anachronos, Evaluation, Simulation, Synthetic Data, and future platforms without importing their domain code.

## G5 — Cross-cloud and on-prem semantic portability

A Bronze `WorkflowSpec` and its logical execution semantics must remain meaningful across supported Alibaba, Volcano, Tencent, Baidu, private-cluster, edge, and future execution environments. Portability is semantic, not merely syntax translation.

## G6 — Bronze-owned canonical contracts

`WorkflowSpec`, task semantics, execution observations, artifact/resource references, and related shared contracts belong to Bronze Dragonflight. No cloud workflow definition, Kubernetes object, Slurm job, or other backend-native object is the canonical workflow model.

## G7 — Reliable recovery

Different failure scopes must have different recovery semantics:

- Engine/process crash → automatic reconciliation.
- Task attempt failure → retry policy.
- Lost execution backend → attempt recovery/failure classification.
- Terminal workflow failure → explicit redrive/restart.

## G8 — Versioned reproducibility

A run should pin an immutable execution snapshot once that detailed model passes the Design Gate. A redrive must not silently change the workflow definition, task definition, or execution policy.

## G9 — Strong operational visibility

Operators need a graph, state timeline, task-attempt history, errors, events, log links, resource references, admission reasons, and recovery actions without reading raw backend objects.

## G10 — Runtime portability

Andormu core semantics must not require Kubernetes, Slurm, Ray, a specific cloud workflow engine, or any single runtime. Backend-specific behavior belongs behind adapters/contracts.

## G11 — Safe dynamic workflows

Conditional branches, fan-out, and subworkflows should be possible without sacrificing durable recovery. Dynamic expansion must be explicit and durably recorded before expanded nodes run.

## G12 — Interoperable events

External lifecycle events should be representable in a CloudEvents-compatible envelope. Lineage integrations such as OpenLineage should be adapters, not Andormu's core state model.

## G13 — Product-quality governance

Multi-tenant namespaces, RBAC, audit, API idempotency, versioning, and compatibility must be designed before implementation.

## G14 — Service-first execution compatibility

A logical task must be executable by an already-running service or worker without requiring process/container lifecycle to equal task lifecycle.

Inline versus deferred/asynchronous completion is an execution-protocol property, not a separate DAG business-node type.

## G15 — Logical admission and high-volume dispatch safety

Andormu owns logical admission of dependency-ready work. It must be able to keep work queued/admitted safely instead of flooding a constrained service, worker pool, or downstream execution target.

Logical admission remains distinct from physical resource admission, placement, quota, topology, preemption, and GPU scheduling.

## G16 — Domain-owned workflow selection

Domain platforms choose or compile the correct workflow for their data/business semantics. Andormu instantiates and executes the supplied workflow without embedding file-type, training, or other domain routing rules.

## G17 — Reuse mature infrastructure

Andormu must integrate rather than reimplement mature infrastructure such as Kafka/MQ, Flink/Spark, Kubernetes, Slurm/Ray, GPU virtualization, object storage, databases, service discovery, and observability systems.

## G18 — One orchestration authority per execution graph

When another mature system owns an internal execution DAG, Andormu should normally treat that system's execution as one opaque TaskAttempt. Andormu must not create a second competing state machine for the same graph.
